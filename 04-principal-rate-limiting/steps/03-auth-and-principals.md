# Step 3. Auth strategy and principals

## Purpose

Create the client identity for Lab 4. The auth strategy checks the header `apikey` against the Identity directory named `default`. Three principals each have their own imported API key. This step does not create an AI Consumer or an Identity group.

## What will be created or modified

| File | Resources |
|---|---|
| `config/03-auth-strategy.yaml` | Auth strategy `sts-lab04-key-auth` |
| `config/05-principals.yaml` | `sts-lab04-principal-t1`, `sts-lab04-principal-t2`, `sts-lab04-principal-t3`, and one imported API key on each |

The auth strategy enables principal lookup in the directory `default`. A missing or unknown key is rejected, and the `apikey` header is removed before the upstream request. The principal YAML contains only deferred references to `STS_LAB04_TIER1_KEY`, `STS_LAB04_TIER2_KEY`, and `STS_LAB04_TIER3_KEY`; the key values are read from the environment only when the plan is applied.

The directory is declared with `_external`. The plan looks it up by name and does not adopt it. Do not plan this file with sync mode.

Each principal stores two metadata fields:

| Principal | `tier` | `counter_key` |
|---|---|---|
| `sts-lab04-principal-t1` | `t1` | `sts-lab04-principal-t1` |
| `sts-lab04-principal-t2` | `t2` | `sts-lab04-principal-t2` |
| `sts-lab04-principal-t3` | `t3` | `sts-lab04-principal-t3` |

`tier` identifies the tier. Scenario 2 maps it to 2, 4, or 6 requests, and scenario 3 maps it to 100, 200, or 400 tokens. Those numbers are defined in the policies. `counter_key` supplies a stable, different token-counter key for each principal in scenario 3. Scenario 2 does not read it. These metadata fields configure rate limiting; they do not grant access.

## Required prerequisites

Step 2 is complete in this shell, or you load `$LABS_DIR/.env` again below. The provider check in step 2 printed `sts-lab04-openai`. The directory `default` already exists.

## Generate the three client keys

Run this once. For each name that is missing or empty, it appends a new key to `$LABS_DIR/.env`. A name that already has a value is left as it is. The command prints the lengths, not the keys.

```bash
umask 077
touch "$LABS_DIR/.env"
if [[ -s "$LABS_DIR/.env" && -n "$(tail -c 1 "$LABS_DIR/.env")" ]]; then
  printf '\n' >>"$LABS_DIR/.env"
fi
for name in STS_LAB04_TIER1_KEY STS_LAB04_TIER2_KEY STS_LAB04_TIER3_KEY; do
  if ! grep -q "^${name}=..*" "$LABS_DIR/.env"; then
    printf '%s=%s\n' "$name" "$(openssl rand -hex 24)" >>"$LABS_DIR/.env"
  fi
done

set -a
source "$LABS_DIR/.env"
set +a

echo "tier 1 key length: ${#STS_LAB04_TIER1_KEY}"
echo "tier 2 key length: ${#STS_LAB04_TIER2_KEY}"
echo "tier 3 key length: ${#STS_LAB04_TIER3_KEY}"
```

A length of 0 means that variable is empty. A key generated by this block has 48 hexadecimal characters. Existing non-empty values are preserved. The variable names must match the YAML exactly.

## Commands to preview changes

Preview the auth strategy, then the principals. Konnect is not changed. The API keys are not written into the plan files.

```bash
set -a
source "$LABS_DIR/.env"
set +a

mkdir -p "$LABS_DIR/04-principal-rate-limiting/plans"

kongctl plan \
  --mode apply \
  --filename "$LABS_DIR/04-principal-rate-limiting/config/03-auth-strategy.yaml" \
  --output-file "$LABS_DIR/04-principal-rate-limiting/plans/auth-strategy.apply-plan.json"

kongctl plan \
  --mode apply \
  --filename "$LABS_DIR/04-principal-rate-limiting/config/05-principals.yaml" \
  --output-file "$LABS_DIR/04-principal-rate-limiting/plans/principals.apply-plan.json"
```

Read the two previews. The first creates `sts-lab04-key-auth`. The second creates the three principals and the imported keys `sts-lab04-principal-t1-key`, `sts-lab04-principal-t2-key`, and `sts-lab04-principal-t3-key`. It does not create or update the directory. The plan must not contain the key values.

`--mode apply` limits each preview to that file. Without it, sync mode also deletes resources that are not in the file.

## Commands to apply changes

Apply the saved previews in this order. Do not add `--write-secrets` or `--secret-output-dir`. These are imported keys supplied by the environment, not keys generated by Konnect.

```bash
kongctl apply \
  --plan "$LABS_DIR/04-principal-rate-limiting/plans/auth-strategy.apply-plan.json" \
  --auto-approve \
  --output json

kongctl apply \
  --plan "$LABS_DIR/04-principal-rate-limiting/plans/principals.apply-plan.json" \
  --auto-approve \
  --output json
```

Konnect does not return the API key values. Imported key material is create-only: changing a value in `.env` and reapplying the same key ref does not rotate it. Rotation requires a new key ref and secret, followed by a reviewed removal of the old key after clients have switched.

## Commands to verify configuration

The strategy name is `sts-lab04-key-auth`, the type is `key-auth`, and the header name is `apikey`. Principal lookup is enabled on directory `default`.

```bash
kongctl get ai-gateway auth-strategies \
  --gateway-id "$AI_GATEWAY_ID" \
  sts-lab04-key-auth \
  --output json \
  --jq '{
    name,
    type,
    key_names: .config.key_names,
    hide_credentials: .config.hide_credentials,
    realms: .config.identity_realms,
    principals: .config.principals

```

Each command prints one principal. `tier` is `t1`, `t2`, or `t3`. The command does not print the key.

```bash
for name in sts-lab04-principal-t1 sts-lab04-principal-t2 sts-lab04-principal-t3; do
  kongctl get id principals \
    --display-name "$name" \
    --output json \
    --jq '.[0] | {display_name, type, tier: .metadata.tier, counter_key: .metadata.counter_key}'

```

The key list prints the name and the type `imported`. It does not print the secret.


## Explanation of the policy behavior

The auth strategy finds a principal. It does not apply a rate. The metadata is read later by the request policy and the token policy. A missing or unknown key fails in this strategy before either policy runs. That failure is HTTP 401. No AI Consumer is created for these keys.
